## 1. 系统概述

### 1.1 项目简介

EasyXT_Study 是一个基于 Python + Qt 的股票数据管理系统，集成了：

- **多源数据下载**: 支持QMT/迅投API、Tushare等数据源
- **双模式存储**: Parquet文件归档 + DuckDB物理表高性能查询
- **智能数据管理**: 自动识别存储模式、增量更新、数据校验
- **可视化界面**: PyQt5桌面应用，支持数据查看、统计、分析

### 1.2 核心特性

| 特性 | 描述 |
|------|------|
| 🔄 **双模式存储** | Parquet文件 + DuckDB物理表，可单独或同时使用 |
| ⚡ **高性能查询** | COPY命令、并行处理、智能缓存 |
| 🤖 **智能检测** | 自动识别可用数据源并推荐最优方案 |
| 📊 **多种周期** | 日线(1d)、分钟线(1m/5m/15m/30m/60m)、周线(1w)、月线(1M)、Tick |
| 🔧 **灵活配置** | 通过YAML配置文件控制所有行为 |
| 🛡️ **数据安全** | 双重备份、完整性校验、错误恢复 |

## 2. 架构设计

### 2.1 整体架构

系统采用**三层架构**：

#### 第一层：表示层 (UI)
- **职责**: 用户交互、数据展示、操作反馈
- **组件**:
  - `LocalDataManagerWidget`: 数据下载和管理
  - `AdvancedDataViewerWidget`: 数据查询和可视化
  - `MainWindow`: 主窗口框架

#### 第二层：业务逻辑层 (Core)
- **职责**: 数据处理、策略执行、协调各模块
- **组件**:
  - `DataDownloadStrategy` (抽象基类): 定义下载策略接口
    - `DailyDataStrategy`: 日线数据策略
    - `WeeklyDataStrategy`: 周线数据策略
    - `MonthlyDataStrategy`: 月线数据策略
    - `MinuteDataStrategy`: 分钟线策略
    - `TickDataStrategy`: Tick数据策略
  - `ParquetManager`: 统一存储管理入口
  - `DatabaseTableManager`: 物理表操作
  - `DataSourceDetector`: 数据源检测
  - `ViewManager`: 视图管理

#### 第三层：存储层 (Storage)
- **职责**: 数据持久化、文件I/O、数据库操作
- **组件**:
  - `ParquetStorageManager`: Parquet文件读写
  - DuckDB数据库引擎

### 2.2 数据流架构

```
用户触发下载
     ↓

     ↓ 获取参数（日期范围、标的列表、数据类型、存储选项）

     ↓

     ↓

     ↓ 数据清洗、类型转换、添加元数据
     ↓

     ├─→ [Parquet模式] → _save_to_parquet_only()
```

## 3. 双模式数据存储

### 3.1 模式概览

系统支持**三种独立的存储方式**，可自由组合：

| 组合方式 | Parquet文件 | DuckDB物理表 | 适用场景 |
|---------|------------|-------------|---------|
| ☑️ 仅Parquet | ✅ 保存 | ❌ 不保存 | 长期归档、数据共享 |
| ☑️ 仅DuckDB表 | ❌ 不保存 | ✅ 保存 | 高频查询、低延迟需求 |
| ☑️ 双重存储 | ✅ 保存 | ✅ 同时保存 | 重要数据双重保险 |

### 3.2 UI界面布局

在"数据管理"页面的初始化区域：

```
第一行: ☐ 首次初始化：删除重建表结构

第二行: 💾 数据存储: （复选框组合）
        ☑️ 保存Parquet文件    ☐ 保存到DuckDB表
        
第三行: 🧪 运行模式: （独立区域）
        ○ 测试模式   ● 正式模式
```

### 3.3 各模式详细说明

#### 3.3.1 Parquet模式（📁 文件归档）

**工作原理**:
```
DataFrame → 保存为 .parquet 文件 → 在 stock_views.duckdb 创建视图映射
```

**优势**:
- ✅ 文件可移植（复制到其他电脑即可使用）
- ✅ 支持长期归档和备份
- ✅ 可被其他工具读取（Pandas、Spark、PyArrow等）
- ✅ 列式压缩，节省磁盘空间
- ✅ 天然分区（按年/月/股票代码）

**劣势**:
- ❌ 查询时需打开+解析+解压，首次较慢
- ❌ 需要维护视图定义
- ❌ 大量小文件可能影响性能

**适用场景**:
- 历史数据长期保存
- 多个应用程序/服务器共享数据
- 大数据分析（配合Spark等工具）
- 需要离线访问数据

**文件结构**:
```
D:\MyStockData\
└── Parquet\
    └── kline\
        ├── daily\
        │   ├── year=2026\
        │   │   ├── month=01\
        │   │   │   ├── 000001.SZ.parquet
        │   │   │   ├── 600025.SH.parquet
        │   │   │   └── ...
        │   │   └── month=02\
        │   └── ...
        ├── weekly\
        ├── monthly\
        └── ...
```

#### 3.3.2 数据库表模式（⚡ 高性能）

**工作原理**:
```
DataFrame → 直接 INSERT/COPY 到 stock_data.duckdb 的物理表中
```

**优势**:
- ✅ 查询速度极快（无文件IO开销）
- ✅ 内置索引和统计信息
- ✅ DuckDB优化缓存机制
- ✅ 无需维护视图
- ✅ 支持事务和ACID特性

**劣势**:
- ❌ 数据在单一数据库文件内，不易移植
- ❌ 数据库损坏风险（需定期备份）
- ❌ 不易与其他工具共享

**适用场景**:
- 高频实时查询（如盘中监控）
- 策略回测（需要快速遍历大量数据）
- 单机使用，不需要共享
- 对延迟敏感的应用

**表结构示例** (`stock_daily`):
```sql
CREATE TABLE IF NOT EXISTS stock_daily (
    stock_code VARCHAR(20) NOT NULL,    -- 股票代码
    symbol_type VARCHAR(10),              -- 类型: stock/index/fund
    date DATE NOT NULL,                  -- 日期
    period VARCHAR(10),                   -- 周期: 1d
    open DOUBLE,                          -- 开盘价
    high DOUBLE,                          -- 最高价
    low DOUBLE,                           -- 最低价
    close DOUBLE,                         -- 收盘价
    volume BIGINT,                        -- 成交量
    amount DOUBLE,                        -- 成交额
    adjust_type VARCHAR(10),              -- 复权类型: none/qfq/hfq
    factor DOUBLE,                        -- 复权因子
    created_at TIMESTAMP,                 -- 创建时间
    updated_at TIMESTAMP,                 -- 更新时间
    
    PRIMARY KEY (stock_code, date, period, adjust_type)
);
```

#### 3.3.3 双重存储模式（🎯 推荐）

**工作原理**:
```
DataFrame 
    ↓ 【步骤1】保存到 Parquet 文件（用于归档备份）
    ↓ D:\MyStockData\Parquet\kline\daily\000001.SZ.parquet
    
    ↓ 【步骤2】COPY 转储到 DuckDB 表（用于快速查询）
    ↓ stock_data.duckdb → stock_daily 表
    
    ↓ 【步骤3】刷新视图（可选）
    ↓ stock_views.duckdb → stock_daily 视图
```

**优势**:
- ✅ 兼具两者优点：可移植 + 高性能
- ✅ 数据双重保险，降低丢失风险
- ✅ 归档用Parquet，查询用物理表
- ✅ 可独立管理两种数据源

**劣势**:
- ❌ 磁盘空间占用翻倍
- ❌ 写入时间略长（需两次保存）
- ❌ 需要同步两份数据的一致性

**适用场景**:
- 重要数据必须安全保存
- 既需要快速查询，又需要长期归档
- 磁盘空间充足
- 对数据可靠性要求高

**性能对比**:

| 操作 | 仅Parquet | 仅DuckDB | 双重存储 |
|------|----------|----------|---------|
| 写入1000条 | ~0.5s | ~0.12s | ~0.52s |
| 写入10000条 | ~1.2s | ~0.35s | ~1.5s |
| 查询1000条 | ~50ms | ~20ms | ~20ms (使用表) |
| 磁盘占用 | ~50MB | ~45MB | ~95MB |

## 4. 数据库文件分离

### 4.1 设计理念

**问题**: 早期版本将视图和数据混在同一个数据库文件中，导致：
- 文件体积过大（视图元数据 + 实际数据混合）
- 备份困难（需要备份整个大文件）
- 维护复杂（不清楚哪些是视图、哪些是表）
- 性能干扰（视图解析影响数据查询）

**解决方案**: 分离为两个独立的数据库文件

### 4.2 文件结构

```
D:\MyStockData\
├── Parquet\                    ← Parquet文件存储区
│   └── kline\
│       ├── daily\
│       ├── weekly\
│       └── monthly
│
├── stock_data.duckdb          ← 【物理表数据库】🆕
│   ├── stock_daily            ← 包含实际数据的表
│   ├── stock_weekly
│   ├── stock_monthly
│   ├── stock_1m
│   ├── stock_5m
│   ├── stock_15m
│   ├── stock_30m
│   ├── stock_60m
│   └── stock_tick
│
└── stock_views.duckdb         ← 【视图数据库】🆕
    ├── stock_daily            ← 仅包含视图定义
    │   └─ CREATE VIEW AS SELECT * FROM read_parquet(...)
    ├── stock_weekly
    ├── stock_monthly
    └── ... (其他视图)
```

### 4.3 配置文件设置

```yaml
# config/data_config.yaml
database:
  # 物理表数据库（存储实际数据）
  data_db:
    dbfile: "stock_data.duckdb"
    description: "物理表数据库（存储实际数据）"
    
  # 视图数据库（仅存储视图定义）
  view_db:
    dbfile: "stock_views.duckdb"
    description: "视图数据库（仅包含视图定义）"
```

### 4.4 优势对比

| 特性 | 单文件方案 | 双文件方案 ✅ |
|------|-----------|-------------|
| **文件清晰度** | 混合在一起，难以区分 | 职责明确，一目了然 |
| **备份策略** | 必须整体备份 | 可分别备份（视图库很小） |
| **文件大小** | 可能很大（GB级） | 视图库通常 < 100MB |
| **并发访问** | 读写互斥 | 可独立锁定，减少冲突 |
| **迁移成本** | 需传输整个大文件 | 只需迁移需要的部分 |
| **故障恢复** | 全部不可用 | 一个损坏不影响另一个 |

## 5. 数据源自动检测

### 5.1 功能概述

`DataSourceDetector` 是一个智能检测器，用于在查询前自动识别可用的数据源。

**核心能力**:
1. 检测 Parquet 视图是否可用（通过检查视图库中的视图定义）
2. 检测物理表是否有数据（通过检查表记录数）
3. 智能推荐最佳查询方式
4. 支持手工覆盖（通过参数或配置）
5. 提供友好的状态消息

### 5.2 使用方法

#### 方式1: 自动推荐（默认）

```python
from src.core.data.storage.data_source_detector import DataSourceDetector

detector = DataSourceDetector(config)

# 自动检测并推荐
recommended, reason, sources = detector.get_recommended_source('daily')
print(f"推荐: {recommended}")
print(f"原因: {reason}")
# 输出: 推荐: database / 原因: 仅物理表可用（125000条）- 高性能查询
```

#### 方式2: 手工指定

```python
# 强制使用Parquet视图
success, msg, details = detector.select_source('daily', source='parquet')

# 强制使用物理表
success, msg, details = detector.select_source('daily', source='database')
```

#### 方式3: 配置优先级

```yaml
# config/data_config.yaml
storage:
  query_priority:
    preferred: "database"    # 默认优先使用物理表
    fallback: true           # 如果不可用，回退到Parquet
```

```python
# 使用配置文件的设置
success, msg, details = detector.select_source('daily', source='auto')
```

#### 方式4: 获取查询连接（便捷方法）

```python
# 一站式获取连接
result = detector.get_query_connection('daily', preferred_source=None)

if result:
    conn, table_name = result
    df = conn.execute(f"SELECT * FROM {table_name} LIMIT 10").df()
    conn.close()
else:
    print("无可用的数据源")
```

#### 方式5: UI选项列表（静态方法）

```python
# 获取下拉框选项
options = DataSourceDetector.get_available_options()
for opt in options:
    print(f"{opt['label']}: {opt['description']}")
# 输出:
# 🤖 自动推荐: 根据数据量智能选择最优数据源
# 📁 Parquet视图: 通过视图查询Parquet文件（适合归档数据）
# ⚡ 物理表: 直接查询DuckDB物理表（高性能）
```

### 5.3 智能推荐算法

```python
def get_recommended_source(self, data_type):
    """
    推荐逻辑：
    
    1. 两者都可用 → 选择数据量更大的那个
       （假设数据量大的更完整）
       
    2. 仅一个可用 → 直接推荐可用的那个
       
    3. 都不可用 → 返回 'none'，提示先下载数据
    """
    sources = self.detect_available_sources(data_type)
    
    parquet_available = sources['parquet']['available']
    database_available = sources['database']['available']
    
    if parquet_available and database_available:
        # 比较数据量
        if db_count >= parquet_count:
            return 'database', "两者都可用，推荐物理表（更快）"
        else:
            return 'parquet', "两者都可用，推荐Parquet（更完整）"
            
    elif database_available:
        return 'database', f"仅物理表可用（{count}条）"
        
    elif parquet_available:
        return 'parquet', f"仅Parquet视图可用（{count}条）"
        
    else:
        return 'none', "无可用的数据源，请先下载数据"
```

| `stock_60m` | 60分钟线 | TIMESTAMP | ~1500万条/年 |
| `stock_tick` | Tick数据 | TIMESTAMP | ~数十亿条/年 |

**三级性能优化策略**:

```python
def save_to_table(self, df, table_name, data_type, mode='upsert', use_copy=True):
    """
    根据数据量自动选择最优写入策略：
    
    Level 1: copy_from_parquet (最高性能)
        - 条件: mode='copy_from_parquet' 或 use_copy=True 且 count > 1000
        - 实现: 先保存临时Parquet → COPY FROM → 导入DuckDB
        - 速度: 比INSERT快 5-10倍
        
    Level 2: copy_command (高性能)
        - 条件: use_copy=True 且 1000 < count <= 50000
        - 实现: 注册DataFrame → INSERT...SELECT批量操作
        - 速度: 比逐行INSERT快 3-5倍
        
    Level 3: insert (标准)
        - 条件: 其他情况（count <= 1000 或 use_copy=False）
        - 实现: 传统逐行INSERT
        - 速度: 最慢但最兼容
    """
```

**UPSERT实现**:

```python
def _upsert_operation(self, df, table_name, time_col, conn):
    """
    UPSERT = DELETE旧数据 + INSERT新数据
    
    示例：
    输入: df包含 2026-04-01 ~ 2026-04-10 的日线数据
    
    执行：
    1. DELETE FROM stock_daily 
       WHERE stock_code IN ('000001.SZ')
         AND date >= '2026-04-01'
         AND date <= '2026-04-10'
         
    2. INSERT INTO stock_daily SELECT * FROM df_temp
    
    结果: 该时间范围内的数据被完全替换（原子操作）
    """
```

## 9. 性能优化策略

### 9.1 写入性能优化

#### 三级策略自动选择

```
数据量判断
    ↓
≤ 1000 条?
    ↓ Yes                              No
标准INSERT                         1000-50000 条?
    ↓                                 ↓ Yes
逐行插入                            COPY命令
(最慢但最稳定)                        (INSERT...SELECT)
                                    ↓ No
                               > 50000 条?
                                   ↓ Yes
                              COPY转储
                              (从临时Parquet导入)
                              (最快!)
```

**性能基准测试结果**:

| 数据量 | 标准INSERT | COPY命令 | COPY转储 |
|--------|-----------|---------|---------|
| 100条 | 0.05s | 0.03s | 0.08s |
| 1,000条 | 0.35s | 0.12s | 0.18s |
| 10,000条 | 2.8s | 0.85s | 0.52s |
| 100,000条 | 28s | 6.5s | 3.2s |
| **加速比** | 1x | **3-5x** | **5-10x** |

#### UPSERT优化

传统UPSERT（逐行比较）很慢，我们的实现：

```python
# 传统方式（慢）
for each row in new_data:
    if exists in old_data:
        UPDATE row
    else:
        INSERT row

# 我们的方式（快）
DELETE FROM table 
WHERE stock_code IN (new_codes) 
  AND date >= min(date) AND date <= max(date)

INSERT INTO table SELECT * FROM new_data

# 速度提升: 10-50倍（取决于新旧数据重叠程度）
```

### 9.2 读取性能优化

#### DuckDB缓存机制

DuckDB内置多层缓存：

```
查询请求
    ↓
Level 1: 结果缓存（相同SQL直接返回）
    ↓ Miss
Level 2: 数据页面缓存（热数据在内存）
    ↓ Miss
Level 3: 操作系统文件缓存（OS预读）
    ↓ Miss
Level 4: 磁盘IO（最慢）
```

**优化建议**:
- 频繁使用的查询保持相同SQL（命中L1）
- 保持连接不关闭（保留L2缓存）
- 使用SSD硬盘（提升L4性能）

#### 物理表 vs 视图查询性能

| 操作 | Parquet视图 | 物理表 | 加速比 |
|------|-----------|--------|-------|
| 首次查询1000条 | ~50ms | ~20ms | **2.5x** |
| 重复查询1000条 | ~25ms | ~5ms | **5x** |
| 聚合统计（COUNT/MAX/MIN） | ~40ms | ~8ms | **5x** |
| 范围查询（1个月） | ~80ms | ~15ms | **5.3x** |
| JOIN操作 | ~150ms | ~25ms | **6x** |

### 9.3 内存优化

#### 批量处理

```python
# ❌ 错误：一次性加载所有数据
all_data = pd.DataFrame()  # 可能耗尽内存
for symbol in symbols:
    data = download(symbol)
    all_data = all_data.append(data)  # 内存持续增长

# ✅ 正确：分批处理
batch_size = 1000
for i in range(0, len(symbols), batch_size):
    batch = symbols[i:i+batch_size]
    batch_data = download_batch(batch)
    save_to_disk(batch_data)  # 立即保存，释放内存
    del batch_data  # 显式释放
```

### 10.3 存储问题

#### Q6: Binder Error: Contents of view were altered: types don't match!

**原因**: 视图定义的列类型与实际Parquet文件不一致

**常见情况**:
- stock_code 字段在某些情况下变成 VARCHAR（应为VARCHAR，但如果原定义为INTEGER就会出错）
- 新增或删除了列
- 数据类型变更（如 float32 → float64）

**解决方案**:
```python
# 方法1: 删除并重建视图
view_manager.rebuild_all_views()

# 方法2: 刷新特定类型的视图
view_manager.refresh_view('daily')

# 方法3: 如果仍有问题，删除旧的Parquet文件重新下载
```

**预防措施**:
- 不要手动修改Parquet文件的schema
- 保持数据转换逻辑的一致性
- 定期检查视图与实际数据的一致性

#### Q7: TypeError: connect(): incompatible function arguments (mode='read_write')

**原因**: DuckDB连接参数错误

**错误代码**:
```python
duckdb.connect(path, mode='read_write')  # ❌ 错误!
```

**正确代码**:
```python
duckdb.connect(path, read_only=False)  # ✅ 正确!
```

**已修复位置**: `database_table_manager.py` 第244-248行

#### Q8: 数据保存到Parquet后，date列消失

**原因**: Parquet保存时未显式创建date列，日期信息只在索引中

**解决方案**: 已修复，在 `parquet_storage_manager.py` 中确保:
```python
if data_type in ['1w', '1M', 'weekly', 'monthly']:
    if 'date' not in df.columns:
        df['date'] = pd.to_datetime(df.index).dt.date
        logging.info(f"创建date列")
```

#### Q12: 查询大数据集时内存不足

**解决方案**:
```python
# 使用分块查询
chunk_size = 100000
offset = 0
while True:
    sql = f"""SELECT * FROM stock_daily 
           ORDER BY date 
           LIMIT {chunk_size} OFFSET {offset}"""
    chunk = conn.execute(sql).df()
    if len(chunk) == 0:
        break
    process(chunk)  # 处理当前块
    offset += chunk_size
    del chunk  # 释放内存
```
